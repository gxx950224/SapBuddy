# FS 合同（编号、状态、字段、证据）

## 状态行

```
状态：草稿 · 待确认 <N> 项 · 更新 <YYYY-MM-DD>
项目 / 模块：… ｜ 系统与客户端：… ｜ 需求提出人：…
```

`<N>` 必须等于正文「待确认」表中 Q 的实际条数。

## 编号（本文件内唯一，不重排）

| 前缀 | 含义 | 出现位置 |
| --- | --- | --- |
| R | 业务规则 | 第4节 |
| T | 验收用例 | 第6节 |
| Q | 待确认问题 | 第7节；正文可用【待确认 Q-xx】 |
| E | 取证记录 | 附录 A；正文「依据」列引用 |
| M | 消息 | 第5节消息表 |

不使用旧编号：`REQ` / `BR` / `EV` / `TC` 等。

## 字段写法

- 用**业务名**，就地写清：类型、必填、取值来源与格式、空值含义。
- 同一字段在不同位置格式不同时，各自写清换算。
- 不发明跨文档人造字段键（field/source/action/…）。

## 规则与验收

每条 R 必须有：条件 / 结果 / 异常 / 依据 / 验收（至少一个 T）。
每条 T 必须有：前置 / 输入 / **可核对**的预期（不是「成功」）。
依赖未关闭 Q 的用例：预期写清当前建议值，并标注「依赖 Q-xx；结论变化则本用例失效」；必要时标【阻塞】。

## 依据列

- 系统取证 → `E-xx`
- 业务口述 / 会议确认 → 写「需求确认（日期或场合）」，**不要**伪装成 E
- 未核实建议 → 标【建议】

## 标记

- 未知：【待确认 Q-xx】
- 不适用：【不适用：原因】
- 建议未确认：【建议】

## 增强类章节分工

- 第2节：业务流程**整体**现状（含未改变部分）
- 第3节：只写**本次改变**的动作

## 证据

证据在附录 A（查了什么 / 结果 / 限制与结论）。正文引用编号，不把证据详情塞进第2/3节。
修订历史：默认**不**进 FS 正文（版本由交付/流转平台承载）。若项目要求文档内签署追溯，再加「修订记录」小节——需产品确认后启用。

## 页脚

可保留 `Generated by SapBuddy`。生成后删除模板顶部 `<!-- 写作约定 -->` 注释块。

## HTML 与接口 JSON

定稿后必须按 `archive-html.md` 产出无 logo 的 `FS.html`；接口类必须附样例 JSON（正文 + 独立文件）。
