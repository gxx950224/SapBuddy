## 3. 接口设计

### 3.1 交互边界

| 项目 | 定义 |
| --- | --- |
| 业务用途与成功标志 | <对方拿到什么、能据此完成什么业务；什么结果才算这次交互成功> |
| 调用发起方 → 被调用方 | <哪边主动发起> |
| 业务数据源 → 业务数据目标 | <数据从哪个系统产生、最终落在哪里。可能与调用方向相反> |
| 协议 / 同步或异步 | <已定的协议；异步时说明返回的是受理还是完成> |
| 触发方式与频率 | <业务事件 / 定时 / 人工；时间窗口与时区> |
| 备选方案与取舍 | <考虑过的其它做法，为什么选这个；没有则写「无」> |

### 3.2 消息与字段

消息：<名称>（请求 / 响应 / 回调），方向 <A → B>

| 路径 | 含义 | 类型(长度) | 必填 | 取值来源与换算 | 空值处理 |
| --- | --- | --- | --- | --- | --- |
| Header.OrderId | 采购订单号 | CHAR(10) | 是 | 取自 EKKO-EBELN，补足前导零 | 为空即拒绝 |
| Items[].Price | 行项目净价 | DEC(11,2) | 是 | EKPO-NETPR，按价格单位换算为单价 | 0 与空分别处理：0 合法，空拒绝 |
| Items[].DelivDate | 交货日期 | CHAR(10) | 否 | EKPO-EINDT，`YYYY-MM-DD` | 空表示未定，不参与计算 |

<`Items[]` 表示重复集合，路径在全文保持一致。多级结构按实际层级展开，不限制层数。
 上面三行是填写示范，生成实际 FS 时替换。>

固定部分：编码 <UTF-8 / 其它>；日期格式 <…>；标识类字段保留前导零 <是/否>。

### 3.3 传输范围

| 项目 | 规则 |
| --- | --- |
| 全量 / 增量 | <哪一种；两者都要时写清切换条件> |
| 筛选条件 | <组织、业务类型、状态等；可与增量叠加> |
| 增量依据 | <变更时间 / 序号 / 事件；是否覆盖新增、修改、删除、冲销> |
| 边界与迟到 | <起止是否包含、时区、同时间戳的次序、迟到记录怎么处理> |
| 水位推进 | <在哪个节点推进：发送成功 / 受理成功 / 业务成功> |
| 空批次 | <没有数据时是否发送、如何记录> |
| 首次与补传 | <初始范围、历史补传、断点恢复> |

### 3.4 结果与失败

| 场景 | 期望处理 | 由谁确认结果 |
| --- | --- | --- |
| 正常完成 | <响应里返回什么，对端据此判断什么> | <接收方 / 人工核对> |
| 重复请求 | <业务键是什么；再次到达时返回原结果还是拒绝> |  |
| 同键不同内容 | <比较哪些字段；冲突怎么处理> |  |
| 部分成功 | <业务原子单元是一行、一张单据还是整批；已成功部分是否保留> |  |
| 超时或结果未知 | <先用什么核对真实结果；确认前是否允许重试> |  |
| 需要补偿 | <SAP 与对端各自的实际状态；谁来修> |  |

结论层次写清楚：<传输到达 / 已受理 / 业务完成>分别以什么为证据——三者不能相互替代。

### 3.5 日志与对账

- **日志**：<记录哪些关联标识、状态、业务编号、错误摘要；保留多久。>
- **对账**：<用哪些业务键核对数量或金额，在什么时间窗口，容差多少，差异由谁处理。>
- **技术对象**：<函数 / API / 服务的候选名称与用途，标清是已核实还是待验证。>
### 3.6 样例 JSON（归档必出）

按 3.2 字段表整理**一份可联调的示例**（虚构但类型/必填/格式与表一致）。HTML 归档时把下列代码块原样放入「样例 JSON」节。

**请求示例**

```json
{
  "Header": {
    "OrderId": "4500001234"
  },
  "Items": [
    {
      "Price": 12.50,
      "DelivDate": "2026-11-01"
    }
  ]
}
```

**响应示例**

```json
{
  "Status": "ACCEPTED",
  "BusinessKey": "4500001234",
  "Message": "受理成功"
}
```

说明：路径、嵌套与 3.2 保持一致；空值/0 按表中「空值处理」示范；多消息（请求/响应/回调）各自给一组。未定字段不要编造业务值，标【待确认】或从示例中去掉。
